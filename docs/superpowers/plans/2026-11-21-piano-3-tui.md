# gmail-tui — Piano 3: TUI core — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** L'app TUI funzionante contro `MailStore`: inbox con lista, lettura thread, ricerca, mutazioni (leggi/stella/archivia/label), refresh via Watch, status bar, mouse, keymap vim-ish, help — con il Mock come backend di test e `imap.Store` come backend reale.

**Architecture:** Bubble Tea v2 (Elm architecture). `internal/app.Model` è la radice: routing viste (inbox/thread/search), status bar globale, keymap centrale. Le viste sono sub-model con contratti `Update/View` puri → testabili senza terminale. TUTTE le chiamate store girano in `tea.Cmd` (rete mai bloccante); i risultati tornano come `Msg` tipizzati. `Watch` in una goroutine → `tea.Printf`-style events via canale custom `tea.Cmd` (`waitForChange`). Stili derivati dai slot di `internal/theme` (Piano 1) — nessun hex diretto.

**Tech Stack:** `charm.land/bubbletea/v2`, `charm.land/bubbles/v2` (list, viewport, textinput, help, spinner), `charm.land/lipgloss/v2` — le stesse v2 di pop. Test: Update/View puri contro `mail.Mock`.

**Nota esecuzione:** subagent su GLM-5.3-Flash / glm-5-turbo quando disponibile nella definizione agente; altrimenti general-purpose.

### Task 1 (PREREQUISITO, da review finale Piano 2): mutua esclusione op-vs-op del gate

**Files:** Modify `internal/mail/imap/imap.go` (+watch.go per i comandi watch-side), test in `internal/mail/imap/`.

**Perché:** con le future `tea.Cmd` concorrenti, due op simultanee interleaveano i SELECT (SEARCH/STORE/EXPUNGE agiscono sulla mailbox *selezionata* → silenziosamente la mailbox sbagliata). Il gate oggi serializza watch-vs-op ma NON op-vs-op.

**Cosa fare:**
1. `acquire()` attende `holders == 0 && !idling` (mutua esclusione totale; op serializzate ok per una TUI). Mantenere: holders++ prima del wait, no-op-release dopo Close, escape su closed
2. I comandi watch-side FUORI dai round (`baselineState` in Watch, `recheckNewMail` in reconnect) devono girare dentro un round di gate (acquire → comandi → release), così anche loro non interleaveano con op in flight
3. Documentare il contratto sul doc di MailStore/gate: "le operazioni sono serializzate; una op alla volta"

**Test (discriminant):** due ListMessages concorrenti su mailbox diverse (INBOX e "Archive", 5 mail ciascuna) → entrambe restituiscono i ref della PROPRIO mailbox (pre-fix, l'interleave SELECT produce ref mescolate/mancanti — provare il RED se riproducibile; se il timing non lo rende deterministico, il test comunque asserisce la correttezza post-fix ×N ripetizioni). Più: test esistente tutto verde, `go test -race ./... -count=3` stabile.

- [ ] Steps: RED se catturabile → impl gate esteso + watch-side gate → GREEN → vet/lint/race → Commit `fix(imap): full mutual exclusion in idle gate (op-vs-op and watch-side)`
